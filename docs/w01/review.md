# Exercises and answers

## The week in sixteen sentences {#the}

A processor on its own runs one stream of instructions, fetching, decoding and executing them one after another, and protects nothing. An operating system is the layer of software between every program and the hardware that shares the machine, keeps programs apart and makes the hardware easy to use: a virtual machine, a standard library and a resource manager in one. Programs reach it only through system calls, which use a trap instruction to jump to the kernel's chosen entry and raise the processor from user mode to kernel mode in the same step; xv6 has 21 of them. The OS turns one processor into many virtual ones by switching among programs so fast that each believes it owns the processor, which is why four infinite loops on one processor all printed their letters. How the switch is done, saving one program's registers and restoring another's, is the mechanism; which program runs next is the policy; and a process, a running program, is in xv6 one `struct proc` whose `context` field holds the saved registers. The OS also gives each process a private address space and maps it onto a different part of physical memory, with the hardware translating every load and store. That is why two copies of one program both used address 0x200000 and counted separately. A real machine does all of this all day: 61 processes on 2 processors, each with its own memory. Threads are different on purpose: they share one address space, each with only its own program counter, registers and stack. Two threads adding to one counter lost almost half their additions, because `counter++` is three instructions, load, add and store, and the other thread can load the old value in between. At 1000 loops the bug never showed, because the first thread finished before the second existed, so a passing test proves only that the timing was lucky. A mutex lock turns the three instructions into a critical section that only one thread at a time may enter, which made the answer exact at every size and about 8 times slower. A record of who did each increment showed 86,581 switches in 200,000 increments, so the threads still ran at the same time: the lock only decides where the boundary between them falls. `write()` returns as soon as the bytes are copied into the kernel's page cache in RAM and the page is marked dirty, and Linux writes it to the disk within about 30 seconds. A power cut inside that window loses data the program was told had been written, as 200 MB of dirty memory waiting after `dd` returned showed. `fsync()` closes the window by waiting for the disk, at 1638 µs per write against 0.2 µs, thousands of times the cost, and the persistence part of the course is about being durable without paying that on every write.

## Exercises {#exercises}

Do these with a pencil, with the figures of the sections they name beside you. The answers follow, worked in full. Try each one before you look.

**Exercise 1.** In your own words, say how a system call is different from a normal function call. Name the two things a trap does at the same moment, and say why it matters that a program cannot get one without the other. ([Section 1.4](class-1.md#sec-1-4).)

**Exercise 2.** Four copies of `cpu`, the program of [Section 2.2](class-1.md#sec-2-2), run on one processor. First, before looking back at [Section 2.3](class-1.md#sec-2-3), say how you would make all four of them make progress. Then explain the output of Figure 2.5: what the hardware did, what the OS did, and why the letters do not come out in the order A, B, C, D.

**Exercise 3.** Two copies of `mem` ([Section 3.2](class-1.md#sec-3-2)) both print `address of p: 0x200000`, and their counters do not interfere. Explain how. Then a third copy starts five seconds later, with address randomization switched off, as it was for the first two: what address does it print, and what is the first value of its counter that it prints? Why?

**Exercise 4.** Two threads each add 1000 to a shared counter, and the final value is 2000 every time. Does that prove the program is correct? Answer with the timing argument of [Section 4.6](class-2.md#sec-4-6), using the numbers there.

**Exercise 5.** A counter starts at 20. Thread A will increment it twice and thread B once, each increment being load, add, store as in [Section 4.5](class-2.md#sec-4-5). The events happen in this order: A loads; B loads; A adds and stores; B adds and stores; A loads, adds and stores. Draw the timeline as three rows (A, B, memory), write the counter's value in memory after each event, and give the final value. How many increments were lost?

**Exercise 6.** The vote of [Section 5.4](class-2.md#sec-5-4): the locked program prints 200,000,000 every time. Is anything still happening in parallel? Choose A, B or C, and support your choice with numbers read from Figure 5.10.

**Exercise 7.** Use the two `time` lines of Figure 5.5 (both runs are 100,000,000 loops, so 200,000,000 increments). (a) How many times longer did the locked program take? (b) Check both cpu percentages from the user, system and total times. (c) Divide the locked program's wall-clock time by all 200,000,000 increments of both threads together: how many nanoseconds of wall-clock time does one increment cost? (d) In the broken program, each thread did one increment about every 2.5 ns ([Section 4.6](class-2.md#sec-4-6)). Suppose a single thread, with no lock and no second thread, did all 200,000,000 increments at that rate (a thread alone would probably be a little faster still, with no other core fighting over the counter). How long would it take, and how does that compare with the two locked threads?

**Exercise 8.** An interviewer says: "Two threads each add 1 to a shared integer 100,000 times. The final value is 121,000. Explain what happened and fix it." Answer with four habits that interviewers reward: name the mechanism (what the hardware or the kernel actually did), draw it, give a measured number, and name what your fix costs. Say also whether it could happen on a machine with only one core.

**Exercise 9.** An interviewer says: "Two processes both print a pointer value of 0x200000, and each sees a different number stored there. Explain. Then: could process A read process B's value if it really tried?"

**Exercise 10.** An interviewer says: "Your service calls write() for a new record, gets 13 back, and returns a success reply to the client. The machine loses power two seconds later. The record is gone. How, and what would you change?" Include in your answer how many records per second one thread could save if it called `fsync` after every one, using the 1638 µs of Figure 6.10.

**Exercise 11.** Three readings of real captures. (a) In Figure 6.6, the program's own `openat` returned 3. Why 3, and not 0? (b) In the same figure, the `write` line says 13. List the 13 bytes. (c) In Figure 6.8, `dd` wrote 200 blocks of 1 MiB. How many kB is that, and how does it compare with the `Dirty` line right after it? (d) In the same figure, `dirty_expire_centisecs` is 3000. How many seconds is that, and what does it mean for a program that writes a file and then loses power 10 seconds later?

**Exercise 12.** In your own words, in about eight sentences, explain the three pieces of the course to a friend who has not taken it. For each piece, say what problem it solves and describe the one demo from this week that shows it.

## Answers {#answers}

**Answer 1.** A normal function call jumps to code inside your own program, wherever you choose, and the processor stays in user mode, with the same limited privileges. A system call uses a trap, which does two things at the same moment. It jumps into the kernel, at an entry the kernel set up in advance (the trap handler). And it switches the processor from user mode to kernel mode, which raises the privilege. It matters that the two come together. If a program could raise the privilege without jumping to the kernel's entry, it could run its own code with full privilege and ignore every rule. If it could jump into the kernel without raising the privilege, the kernel could not do its work. Because the only way to get kernel privilege is to land at the kernel's chosen entry, a buggy program cannot scribble on the kernel or reach the disk directly. When the kernel is done, a return instruction drops back to user mode and continues the program.

**Answer 2.** The way to make all four progress is the shape from Figure 2.2: run one for a short moment, stop it, run the next, and keep rotating, fast enough that nobody notices. In Figure 2.5, the hardware did what it always does: it fetched, decoded and executed one instruction stream at a time, on its one processor. The OS, with help from the hardware (a timer that lets it take the processor back from a program that never stops), switched the processor among the four processes, saving one's registers and restoring the next one's. That is why A, B, D and C all appear, round after round, as if each had its own processor. The order is not A, B, C, D because nothing in the programs sets the order: the OS's choice of which process runs next, its policy, decided it, and on another machine or another run the order would be different. Any order is correct.

**Answer 3.** 0x200000 is not a real position in the memory chips. Each process has its own private address space, and 0x200000 is a name inside that space. The OS sets up a separate map for each process, and the hardware translates every load and store through the map of the process that makes it. So process 24113's 0x200000 lands in one place in physical memory and 24114's in another (Figure 3.5 draws two such places). Each counter is a different physical byte, so neither sees the other's additions. A third copy started five seconds later, with randomization off like the first two, prints the same address as they did: 0x200000 on the textbook's machine, and on yours, whatever the first two printed. It is the same program asking for memory in the same way. The first counter value it prints is 1: its counter is a new byte in its own private memory, set to 0 at line a3 and incremented once before the first print, whatever the other two have counted to.

**Answer 4.** No. At 1000 loops the bug simply never got a chance to happen. Creating the second thread takes tens of microseconds. One increment takes about 2.5 ns, so a loop of 1000 takes about 1000 × 2.5 ns = 2.5 µs, a few microseconds. Thread A therefore finishes its whole loop before thread B even exists, and the two never run at the same time, so no update can be lost. The program is exactly as wrong as at 100,000 loops (which takes about 250 µs, so the threads overlap for most of the run, and the answer was 103,902). A passing test only shows that this particular timing did not trigger the bug.

**Answer 5.** The rows, with the counter in memory after each event:

| event | thread A | thread B | memory |
|---|---|---|---|
| 1 | load → 20 | | 20 |
| 2 | | load → 20 | 20 |
| 3 | add → 21, store 21 | | 21 |
| 4 | | add → 21, store 21 | 21 |
| 5 | load → 21, add → 22, store 22 | | 22 |

The final value is 22. Three increments ran, so the right value is 20 + 3 = 23. One increment was lost. B loaded 20 at event 2, before A stored 21 at event 3. So B's store at event 4 wrote 21 again, over A's 21, and the counter stayed at 21 although two increments had run. Which of the two you call lost does not matter: the counter rose by one for two increments. A's second increment, at event 5, ran alone and was not lost.

**Answer 6.** B: both threads were still running at the same time. The final value cannot decide it, because 200,000,000 is also what A then B would give; that is why the record of [Section 5.5](class-2.md#sec-5-5) was needed, and C is right about the method. The record in Figure 5.10 decides it. At 100,000 loops it shows 86,581 thread switches in 200,000 increments, so the lock changed hands about every 200,000 ÷ 86,581 ≈ 2.3 increments, with run lengths like B1, A1, B16, A14. If A had run its whole loop first, there would have been exactly one switch, as in the 1000-loop run (A1000 B1000, 1 switch). So the two threads interleaved tens of thousands of times; the lock only decided that the boundary between them falls between two increments, never inside one. Figure 5.7 is the question as the deck put it.

**Answer 7.** (a) 1.959 ÷ 0.253 ≈ 7.7, so about 8 times longer. (b) Broken: (0.49 + 0.00) ÷ 0.253 ≈ 1.94, about 195%, so nearly two cores busy. Locked: (2.78 + 0.65) ÷ 1.959 = 3.43 ÷ 1.959 ≈ 1.75, which is 175%. Both match the printed percentages. (c) 1.959 s ÷ 200,000,000 = 0.0000000098 s, about 9.8 ns per increment. (d) 200,000,000 × 2.5 ns = 500,000,000 ns = 0.5 s. One thread alone would finish in about 0.5 s, faster than the two locked threads' 1.959 s. The locked threads spend much of their time handing the lock back and forth and waiting for it; the 0.65 s of kernel time and the 175% are signs of that. For a single shared counter, two threads with a lock are slower than one thread.

**Answer 8.** A model answer. The final value should be 200,000, so 200,000 − 121,000 = 79,000 increments were lost. The mechanism: `counter++` compiles to three instructions, load, add and store, and nothing joins them. If thread B loads the counter after thread A has loaded it but before A has stored the new value, both store the same number, and one increment is lost, with no error. Draw the four-step, two-core timeline of Figure 4.10: both load 50, both store 51. On a single-core machine it still happens, more rarely, whenever the timer interrupt lands between a load and its store. The fix: a mutex around the increment, so only one thread at a time can be between the load and the store. The number: on the arm64 Mac of this week's runs, that fix made the program exact at every size and about 8 times slower, with 0.65 s of kernel time spent putting the waiting thread to sleep and waking it. To show the fix works rather than got lucky, run it many times at many sizes; in this guide's runs, a trace ([Section 5.6](class-2.md#sec-5-6)) showed about 86,000 hand-offs, so the threads really did interleave. The trade-off: correctness costs speed, and for a single counter a faster fix exists: one special instruction that does the load, the add and the store as one atomic step, which later weeks teach.

**Answer 9.** Each process has its own address space. 0x200000 is a virtual address: the hardware translates it, on every access, through a map the OS set up for that process, so the same number lands on different physical memory in A and in B. That is why each sees its own value. Could A read B's value if it really tried? No. A has no address that reaches B's memory at all: every address A can use goes through A's map, and A's map does not lead there. Writing past the end of an array in A can only damage A's own memory, or make A crash; it cannot touch B. That is protection, one of the operating system's main jobs. The OS chooses the maps, which is policy; the hardware applies them on every access, which is mechanism. Processes share data on purpose through files and other explicit means; memory is private on purpose, because sharing it by accident is exactly the counter bug of Exercise 8.

**Answer 10.** `write()` copied the record's bytes into the kernel's page cache in RAM and returned 13; the page was marked dirty, and Linux would have written it to the disk within about 30 seconds. The power failed after two seconds, inside that window, so the record was only in RAM and was lost. The 13 meant "the kernel has the bytes", not "the disk has them", and the service replied "success" too early. The change: call `fsync(fd)` after the write and before replying, so the reply is sent only once the disk has the data. The cost, from Figure 6.10: about 1638 µs per fsync'd write against 0.2 µs without, thousands of times more. If each record is one write followed by one fsync, one thread can save at most 1,000,000 µs ÷ 1638 µs ≈ 610 records a second. Real systems avoid paying that on every request. One way is to append records to a log (a file that is only ever added to at its end) and call fsync once for a whole batch. Another, which this guide does not teach, is to copy the record into the memory of a second machine before replying, so that one power cut cannot lose it. The trade-off is durability per request against throughput, the number of requests per second the service can handle.

**Answer 11.** (a) Every program starts with three files already open: 0 is standard input, 1 is standard output and 2 is standard error. `open` returns the lowest free number, so the first file the program opens gets 3. (The loader's two files also got 3, but each was closed again before ours was opened.) (b) h, e, l, l, o (5), a space (6), w, o, r, l, d (11), the newline `\n` (12), and the NUL byte `\0` (13) that C puts after every piece of text in double quotes. (c) 200 × 1 MiB = 200 × 1024 kB = 204,800 kB. Right after `dd` returned, `Dirty` was 204,828 kB, a little more than 204,800: all of dd's data was still in RAM, waiting for the disk. (Dirty is a count at one moment, so it is not exactly 144 + 204,800; [Section 6.5](class-2.md#sec-6-5) says why.) (d) 3000 hundredths of a second is 3000 ÷ 100 = 30 seconds: dirty data can stay in RAM for about 30 seconds before Linux writes it back. A program that writes a file without `fsync` and loses power 10 seconds later has most likely lost the data, because it was probably still only in the page cache.

**Answer 12.** A model answer. An operating system has three big jobs, and the course takes them in turn. The first is virtualization: one computer pretends to be many, so every program behaves as if it had its own processor and its own memory. This week's demos were four copies of a program that never stops, all making progress on one processor because the OS switched among them. And two copies of another program that both used address 0x200000 and still counted separately, because each had a private map of memory. The second is concurrency: keeping things correct when several of them really run at the same time and share data. The demo was two threads adding to one counter: they lost almost half of their additions, because adding one is three separate machine instructions, and a lock fixed it at about eight times the cost. The third is persistence: keeping data safe when the power goes out. The demo was a program writing 13 bytes: `write` said "done" while the bytes were still only in memory, and making sure they reached the disk with `fsync` cost thousands of times more. Each later part of the course takes one of those three jobs apart.
